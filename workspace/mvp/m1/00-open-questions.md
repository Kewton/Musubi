## Q3. 宣言の形だけでは決まらない「実行時の意味」を、誰がどこに持つか

### 何を決めるか
スキーマ（宣言の形）だけでは答えが 1 つに決まらない振る舞いを、誰が決め、どこに書いておくかを決める。例：`list` の中身、画面の部品の描き方、操作の動き、端数や「今日」の数え方（`02` §6.1）。

### なぜ今決める必要があるか
画面（Instant Renderer）・API（data-api）・保存（DO）・静的チェックのどれも、この意味が決まらないと作れないため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. MUSUNEST が見本を動かしながら決め、スキーマの新しい版と一緒に `appspec-schema` に文書で持つ**（おすすめ） | 店頭が実際に動かせる意味だけが契約に入る。スキーマと意味を同じ版で管理できる | 工場の検査の前提とずれる恐れがある（段階 2 で工場側の契約文書と照らしてから固める） |
| B. v0.1 のバイト列を変えずに、v0.1 の意味だけを決める（以前のおすすめ） | スキーマを差し替えずに済む | 見本 3 つは v0.1 では書けないので、成り立たない |
| C. 工場側（CommandAgent）に決めてもらう | 工場の検査とずれない | スキーマの正本はプラットフォームが持つという契約と逆になる。工場側の裁定を待つ間、M1a が止まる |

### おすすめと理由
- **おすすめ**：A
- **理由**：契約を先に決めるのは店頭の仕事であり（`01` §2.1）、見本を動かしながら決めれば、机上で決めた意味が動かないという手戻りが無いため
- **利用者の画面の数字に出る決めごと**は、採点の期待値に効くので、着手前に Q13 で決める。それ以外（画面の部品の描き方など）は、M1a の中で決めて文書に書く

### なぜ今決める必要があるか
M1 の範囲を L2（宣言だけ）に絞るか、L3/L4（アドオンのコードの実行・サンドボックス）まで広げるかで、設計と作業量が大きく変わるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. L2（宣言だけ）の経路に絞り、テンプレ（#38）は M2 へ移す**（おすすめ） | R2 の宣言 → data-api → host（Instant Renderer）→ DO の経路に集中できる | 企画書の「実テンプレの確定・Form A 統合スモーク」のうち、テンプレ側の検証は M1 で終わらない |

### おすすめと理由
- **おすすめ**：A
- **理由**：見本 3 つと MVP のアプリに要るのは、L2 の経路だけであるため。テンプレの構成は、実物の Template App を作る M2 で要件とともに決めるほうが手戻りが少ない

## Q5. ログインが無い間、アプリの API をどこで有効にするか

### 何を決めるか
認証（Google OAuth）が無い M1 の間、ミニアプリの API をどの環境で有効にするかを決める（[`README.md`](./README.md) §7.3）。

### なぜ今決める必要があるか
今の CD は、main へのマージで staging へ、v タグで production へ自動でデプロイする。認証の無い書き込み可能な API が production に出ないように、先に決めておく必要があるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. dev・staging だけで有効にし、production では 404 を返す**（おすすめ） | production にデータが書き込まれる危険を確実に止められる。CD を止めずに済む | 環境による分岐が 1 つ増える（`vars.ENVIRONMENT` で判定し、テストで固定する） |
| B. M1 の間は production への v タグを打たない | コードに環境の分岐を足さずに済む | セキュリティ修正など、ほかの大事な修正を production に出せなくなる |
| C. production でも API を有効にする | 全環境で同じ動きになる | URL を知っていれば、誰でも production の DO に書き込める |

### おすすめと理由
- **おすすめ**：A
- **理由**：production へのデプロイ経路を塞がずに、認証の無い API の公開を確実に防げるため

## Q6. 宣言をどう置くか（R2 に置いて登録する経路）

### 何を決めるか
宣言（M1a は手書きの見本、M1b は工場の納品物から取り出したもの）を、Cloudflare（R2 と D1）に置いて登録する手段を決める。

### なぜ今決める必要があるか
M1a の最初の経路（割り勘を置いて動かす）に要るため。スクリプトの置き場所と、使う資格情報も決まる。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. 手元のスクリプト（publish）が、静的チェックを通してから R2 に置き、D1 に登録する**（おすすめ） | 管理用の API や認証を新しく作らずに済む。通らない宣言は置かれない。M1b では、納品物の manifest を照合してから同じ publish に宣言を渡せる | 開発者が手元から実行する（`.env` の staging の資格情報を使う） |
| B. data-api に管理用の API を作り、そこへ送る | 将来の自動化に向けた API を先に作れる | data-api は外部ルートを持たない規律なので、gateway に管理用の入口と認証が要り、M2 の認可より先に作ることになる |
| C. Builder Plane から Queue 経由で自動で置く | 手作業が無い | M2 の連携 Lv2 の範囲で、M1 を超える |

### おすすめと理由
- **おすすめ**：A
- **理由**：最小の構成で確実に経路を通せるため。手元のスクリプトから R2 / D1 に書き込むのは、CD が D1 マイグレーションを実行するのと同じ「運用者の操作」であり、「Data API が唯一の権限強制点」というリクエスト経路の規律には触れない
- **補足**：staging への見本の配置を CD に組み込むかは、A ができてから決める

## Q7. L2 の納品物の `assurance: partial` を受け入れるか（M1b）

### 何を決めるか
工場の結果に含まれる保証のラベル `assurance: partial` を、MUSUNEST の受け入れ基準として認めるかを決める。

### なぜ決める必要があるか
CommandAgent の headless 契約では「呼び出し側は verdict と assurance の両方で合否を判定する」と決まっているため、プラットフォーム側の受け入れの規則を書いておく必要がある。M1b の Issue を切るときに決めればよい。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. L2 は `verdict: full` を必須にし、`assurance` は `partial` 以上を受け入れる**（おすすめ） | L2 の納品物をそのまま受け入れられる。実行時のスモークの不足は MUSUNEST の e2e（採点のシナリオ）で埋める | 受け入れの規則を、成果物の水準（L2 と L3/L4）で分けて持つ必要がある |
| B. `assurance: full` を常に必須にする | すべての成果物に、工場側での画面の検証まで求められる | L2 は画面のコードを持たないので工場側で画面を動かせず、L2 の納品物が原理的に通らない |

### おすすめと理由
- **おすすめ**：A
- **理由**：L2 の `verdict: full` は「spec の検証は完了した。実行時のスモークはプラットフォーム統合側が受け持つ」という契約上の意味であるため。画面での動きは MUSUNEST の e2e で確かめる

## Q8. 決定的な再検証をどこで実行するか（M1b）

### 何を決めるか
工場の納品物に対する決定的な再検証（offline verifier による同一性の確認）を、どの環境で実行するかを決める。

### なぜ決める必要があるか
M1b の完了条件（連携 Lv1 の ④）を満たす実行環境と、CI への影響を決める必要があるため。M1b の Issue を切るときに決めればよい。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. 所有者の手元で実行する**（おすすめ） | CI に Rust のツールチェーンや外部のバイナリを持ち込まずに済む。ピンした CommandAgent のバイナリの SHA-256 を照合してから実行する | CI のログに自動では残らないので、手順を runbook にまとめて実行の記録を残す |
| B. GitHub Actions（CI）で実行する | PR ごとに自動で再検証され、客観的な記録が残る | ビルド時にネットワーク越しで外部のバイナリを取得しないピンの規律とぶつかり、CI に重いツールチェーンが要る |

### おすすめと理由
- **おすすめ**：A
- **理由**：CI の軽さとピンの規律を保つため。なお、manifest の照合（全ファイルの SHA-256・構成の確認）は TypeScript で作れるので、こちらは CI（e2e）で毎回自動で行う

## Q11. リアルタイム同期（DO の WebSocket）を M1 に入れるか

### 何を決めるか
Durable Object の WebSocket を使ったリアルタイムのデータ同期を、M1 の範囲に入れるかを決める。

### なぜ今決める必要があるか
画面（host）とサーバ（DO）の通信の作り方と、Cloudflare の無償枠への効き方に関わるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|

## Q12. 宣言を Worker でどう持つか（CPU 10 ms 対策）

### 何を決めるか
アプリの宣言（`app.spec.yaml`）を Cloudflare Workers でどう持ち、どう読んで、CPU 時間 10 ms の上限を守るかを決める。

### なぜ今決める必要があるか
リクエストのたびの YAML の解析や静的チェックは CPU を使い、無償枠の上限（10 ms）や昇格トリガー（P-1）に関わるため。見本には集計もあり、計算の量も増える。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. R2 に原本（YAML）を置き、publish の時点で静的チェック済み・正規化済みの形（JSON）も作って一緒に置く**（おすすめ） | Worker の実行時に YAML の解析と静的チェックを省けて、CPU を抑えられる。静的チェックツールがそのまま正規化も受け持てる | 原本と正規化した形の対応を管理する仕組みが要る（JSON 側に原本の SHA-256 を持たせるなど） |
| B. リクエストのたびに R2 から YAML を取得して、解析と静的チェックを行う | R2 に原本だけを置けばよく、publish が単純になる | YAML のライブラリの大きさと解析の CPU が、10 ms の上限に効く |
| C. インスタンスを作るときに、各 DO の SQLite に正規化した宣言を持たせる | 一度作れば、R2 を読まずに DO の中で速く参照できる | 宣言を更新するとき、同じアプリの多数の DO に 1 つずつ伝える必要がある |

### おすすめと理由
- **おすすめ**：A
- **理由**：10 ms に収めやすく、DO の管理も単純に保てるため。どの方式でも、staging で宣言の読み込み・計算・集計の CPU 時間を実測し、`../m0/06-plan-and-limits.md` の昇格トリガーに照らす

## Q13. 利用者の画面の数字に出る、計算の決めごと

### 何を決めるか
見本を動かすときに、宣言の形だけでは答えが 1 つに決まらない計算のうち、**利用者の画面の数字や並びに出るもの**を決める（`02` §6.1）。

### なぜ今決める必要があるか
採点のシナリオの期待値と、M1a のゲートの判定 1（e2e）に直接効くため。作り始めてから変えると、ゲートの期待値が動く。

### 決めごとと、おすすめ

| 決めごと | 出てくる見本 | おすすめ | ほかの案 |
|---|---|---|---|
| 割り勘の端数 | 割り勘 | 1 人あたりは **1 円未満を切り捨て**、余りは**払った人が持つ**（払った人が割る人に入っていなければ、割る人のうち登録が一番早い人が持つ） | 小数のまま計算し、精算の金額だけ丸める ／ 余りを割る人に 1 円ずつ配る |
| 精算の組み方 | 割り勘 | 受け取る人と払う人を、それぞれ**金額の大きい順**に並べて組み合わせる（同じ金額はメンバーの登録順）。送金は多くても「人数 − 1」回 | 送金の回数が最少になる組み合わせを探す（人数が増えると計算が重く、CPU 10 ms に効く） |
| 「今日」「今月」 | タスク管理・ダッシュボード | **日本時間（Asia/Tokyo）**で数える。採点では時計を固定する | 端末の時間帯で数える（人によって「今日」が変わる） |
| 参照されているものを消すとき | 割り勘・タスク管理 | **消せないようにして、理由を出す**（例：「支出に名前が残っています」） | 一緒に消す ／ 名前だけ残して「削除済み」と出す |
| 空のとき | すべて | 合計・件数は **0**。費用が空の活動は、合計では 0 として数える。「1 回あたり」は活動が 0 回なら 0 | 空なら「—」を出す |
| 割り算の表示（平均など） | ダッシュボード | **小数第 1 位まで**（第 2 位を四捨五入） | 整数に丸める |
| 同じ値の並び | ダッシュボード | **メンバーの登録順** | 名前順（日本語の並び順が揺れる） |

### おすすめと理由
- **おすすめ**：上の表の「おすすめ」の列すべて
- **理由**：
  - 端数：割り勘アプリでよくある決め方で、合計が必ず支出の金額と一致する
  - 精算の組み方：誰が計算しても同じ結果になり、計算が軽い。最少回数の保証は無いが、少人数では差が出にくい
  - 日付：仲間うちで「今日」が揃う。利用者ごとの時間帯が要るようになったら、そのときに足す
  - 消すとき：入力済みのデータが黙って消えない
- **採点のシナリオへの影響**：おすすめどおりなら、`02` の §2.3・§3.3・§4.4 の期待値は変わらない
