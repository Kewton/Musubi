## Q1. ゲートで使う「封緘済み golden 割り勘」はどれか

**背景**：CommandAgent の「golden」は、要求文を封緘したスイート（`community-golden-warikan`）であって、アプリそのものではない。スイートを回すたびに別の `app.spec.yaml` ができる。
その中で、R2 に置く形のまま封緘され、再検証まで済んでいる納品物が1つだけある（`README.md` §2.1）。

| 選択肢 | 良い点 | 気になる点 |
|---|---|---|
| **A. 封緘済み bundle（`cm4-delivery-bundle-001`）をピンで固定する**（おすすめ） | manifest の SHA-256・再検証の記録・スキーマのピンの一致がすでにある。ゲートの判定 5（SHA の照合）がそのまま書ける | 中身が小さい（支出1件ごとの計算だけ） |
| B. M1 の中で one-shot で新しく生成したものを使う | 最新の工場で作ったもの | 実行ごとに中身が変わり、判定の基準が期限の直前まで決まらない。所有者の手元の環境に依存する |

**おすすめの理由**：ゲートは「決まったもの」で判定したい。one-shot の生成（連携 Lv1 の ③）は「工場から店頭まで通った」証拠として別に扱う。

## Q2. ゲートの判定 3 の「golden の期待値」を何とするか

**背景**：宣言した判定 3 は「golden のシナリオどおりに入力し、精算結果が golden の期待値と一致する」。ところが：

- golden のスイートには**期待値もシナリオ（入力の例）も無い**（要求文だけ）
- golden の spec は**支出1件ごとの計算しかしない**。「誰が誰へいくら渡すか」は出ない（スキーマ v0.1 では全体参照ができない。`README.md` §2.3）

| 選択肢 | 中身 | 気になる点 |
|---|---|---|
| **A. spec の computed の意味から期待値の表を作り、事前宣言し直す**（おすすめ） | 例：「4人で 4,000 円、A が立て替え」→ 一人あたり 1,000・A が受け取る 3,000。入力の例と期待値を 3〜5 件、**着手前に** `../m0/05-acceptance.md` §7 に追記する | 「精算アプリ」としては物足りない。企画書の割り勘の姿（精算）とは差がある |
| B. 精算（誰が誰へ）まで M1 のゲートに入れる | 企画書の割り勘の姿に近い | スキーマ v0.2（全体参照・精算の標準関数）と golden の再封緘が要る。**工場側の裁定と再計測が必要で、M1 の 2 週間に収まらない** |
| C. 判定 3 を外す | 簡単 | 「動く」の中身が「画面が出る」だけになり、ゲートが弱くなる |

**おすすめの理由**：線を後から動かさないために、**着手前に**期待値を固定する。精算は、スキーマ v0.2 の裁定（工場側）とあわせて M2 の Instant Runtime で扱う。
判定 3 の言い直しは**ゲートの宣言の変更**なので、所有者が行う（宣言の追記として日付を付けて残す）。

## Q3. スキーマ v0.1 が決めていない実行時の意味を、どう決めるか

**背景**：`README.md` §2.4。たとえば `participants: list` の要素が何か、立て替えた人を含むのか、`views` をどう描くか、`actions` が何をするか。

| 選択肢 | 気になる点 |
|---|---|
| **A. MUSUNEST が最小限を決めて appspec-schema に文書で持つ**（おすすめ） | 工場の verifier の前提とずれるおそれ。ずれを見つけたら工場側へ裁定を依頼する |
| B. 工場側でスキーマを v0.2 に上げて決めてもらってから作る | M1 がその裁定を待つ。golden の再封緘も要る |

**決める範囲の案**（M1 の golden が動くのに要る分だけ）：

| 宣言 | M1 の解釈（案） |
|---|---|
| `number` / `string` | JSON の数値・文字列。`number` は有限の数だけ |
| `list` | 文字列の並び（空を許さない。重複を許さない） |
| `views`（type なし） | その entity の一覧。各行に computed を並べる |
| `actions`（op なし） | その entity に1件追加する。validations を data-api で評価してから保存 |
| `permissions` の `subject: minIdentity` ＋ `minIdentity.mode: anonymous` | M1 はログインが無いので、インスタンスの URL を知っていれば読み書きできる（Q5） |

## Q4. 「Form A の経路」を M1 でどこまで作るか（テンプレ #38 の扱い）

**背景**：企画書の Form A は「共通ホスト＋アドオン」で、アドオン（`app-zone/` のコードを esbuild で束ねたもの）を動的に読み込む形まで含む。
しかし golden の割り勘は **L2（spec だけ）**で、アドオンのコードが無い。アドオンが要るのは L3・L4 の成果物からで、MVP の3アプリ（すべて L2）には出てこない。

| 選択肢 | 中身 | 気になる点 |
|---|---|---|
| **A. L2 の経路に絞る**（おすすめ） | R2 の bundle（spec）→ data-api → host の Instant Renderer → DO。テンプレの中身と tarball（#38）は **M2 へ移す** | 企画書の「実テンプレの確定・Form A 統合スモーク」のうち、テンプレ側は M1 で済まない |
| B. L3/L4 のアドオンの読み込みまで作る | テンプレ（core / sdk / app-zone）の中身・tarball の SHA・アドオンの動的読み込み・sandbox | golden では検証できない（アドオンが無い）。L4 の sandbox の設計が要り、2 週間に入らない |

**おすすめの理由**：ゲートと MVP の3アプリが使うのは L2 の経路だけ。テンプレは、Template App（MVP の Form A）を作る M2 で、実物の要件と一緒に決めるほうが手戻りが少ない。

## Q5. ログインが無い間、アプリの API をどこで有効にするか

**背景**：M1 のアプリは誰でも読み書きできる（`README.md` §7.3）。main へのマージは staging へ、v タグは production へ自動で配られる。

| 選択肢 | 気になる点 |
|---|---|
| **A. dev・staging だけで有効。production では 404**（おすすめ） | env で分ける分岐が1つ増える（`vars.ENVIRONMENT` で判定。テストで固定する） |
| B. M1 の間は v タグを打たない | 他の修正（セキュリティなど）を production に出せなくなる |
| C. production でも有効 | production の URL を知っている人なら誰でも production の DO に書ける |

## Q6. bundle をどう配るか

| 選択肢 | 気になる点 |
|---|---|
| **A. 手元のスクリプト（publish）**：manifest とピンを照合 → R2 に置く → D1 に登録（おすすめ） | 人が実行する。資格情報は `.env` の staging 用（アカウント①） |
| B. data-api に管理用の API を作って、そこへ送る | data-api は外部ルートを持たない。gateway に管理用の入口と認証が要り、M2 の認可より先に作ることになる |
| C. Builder Plane から自動で配る（Queue） | 連携 Lv2（M2）の範囲 |

**補足**：publish が R2・D1 に直接書くのは、CD が D1 マイグレーションを当てるのと同じ「運用者の操作」であり、利用者のリクエストの経路ではない（「Data API が唯一の権限強制点」はリクエストの経路の規律）。

## Q7. L2 の bundle の `assurance: partial` を受け入れるか

**背景**：CommandAgent の headless 文書は「呼び出し側は `verdict` と `assurance` の両方で判定する」と書く。golden の bundle は `verdict: full`・`assurance: partial`。
L2 の「full」は、契約上「spec は検証済み。実行時のスモークはプラットフォーム統合が受け持つ」という限定つきの意味である。

| 選択肢 | 気になる点 |
|---|---|
| **A. L2 は `verdict: full` を必須、`assurance` は `partial` 以上を受け入れる。実行時のスモークは MUSUNEST の e2e で埋める**（おすすめ） | 受入の規則を L2 と L3/L4 で分けて書く必要がある |
| B. `assurance: full` を必須にする | golden の bundle が通らない。L2 は工場で画面を動かさないので、L2 の成果物は原理的に通らない |

## Q8. 決定的な再検証をどこで実行するか

| 選択肢 | 気になる点 |
|---|---|
| **A. 所有者の手元**：ピンした revision の CommandAgent のバイナリを使い、その SHA-256 を照合してから offline の verifier を呼ぶ（おすすめ） | CI の証拠にならない。手順を runbook にして記録を残す |
| B. CI | CommandAgent のバイナリの取得とピンが要る（ビルド時にネットワーク越しで解決しない、というピンの規律と衝突する）。Rust のツールチェーンを CI に持ち込むことになる |

**補足**：manifest の照合（全ファイルの SHA-256・余分なファイルが無いこと）は TypeScript で書けるので、こちらは CI（e2e）で毎回回す。

## Q9. ピン差し替えの儀式（1回）の対象は何か

**背景**：儀式＝新旧のピンを並べて照合 → 回帰（再検証・e2e）→ 旧ピンを外す → 1コミットで記録。

| 選択肢 | 気になる点 |
|---|---|
| **A. golden の bundle のピンを足す**（`pins/commandagent.json` に manifest の SHA-256）。あわせて CommandAgent の revision を最新と照合する（おすすめ） | 「差し替え」ではなく「追加」になる。旧→新の差し替えは、次に工場の revision が進んだときに行う |
| B. テンプレの tarball（#38） | Q4 で M2 に移すなら M1 ではできない |
| C. CommandAgent の revision を新しいものへ差し替える | 2026-09-15 時点で main は `031ec74` のまま進んでいない。差し替える先が無い |

## Q11. リアルタイム同期（DO の WebSocket）を M1 に入れるか

**おすすめ：入れない（M2）。** ゲートの判定 4 は「再読み込み・別の端末でデータが残っている」で、同期の即時性は求めていない。
WebSocket を入れると、接続の保ち方（休止の扱い）と無償枠への効き方を別に調べて実測する必要があり、M1 の 2 週間の外に置きたい。

## Q12. spec を Worker でどう持つか（CPU 10 ms 対策）

| 選択肢 | 気になる点 |
|---|---|
| **A. R2 に原本（YAML）を置き、publish の時点で検査済み・正規化済みの形（JSON）も作って一緒に置く**（おすすめ） | 原本と正規化した形の対応を SHA で結ぶ必要がある（正規化した形に原本の SHA を入れる） |
| B. リクエストのたびに YAML を解釈して検査する | YAML のライブラリの大きさと解釈の CPU が 10 ms に効く |
| C. インスタンスの DO に正規化した spec を持たせる | インスタンスが増えると spec の更新が各 DO に散る |

**どれでも**：spec の読み込みと computed の評価の CPU 時間を staging で実測し、`../m0/06-plan-and-limits.md` の昇格トリガーに照らす。
