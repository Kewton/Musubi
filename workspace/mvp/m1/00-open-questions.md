## Q1. ゲートで使う「封緘済み golden 割り勘」はどれか

### 何を決めるか
M1 の受入ゲート判定で合否基準として使用する「封緘済み golden 割り勘アプリ」の実体をどれにするかを決める。

### なぜ今決める必要があるか
CommandAgent の「golden」は要求文のスイート（`community-golden-warikan`）であり、実行ごとに生成される `app.spec.yaml` の内容が異なる。合否判定の基準となる確定した成果物を着手前に 1 つに定めておく必要があるため（[`README.md`](./README.md) §2.1 参照）。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. 封緘済み bundle（`cm4-delivery-bundle-001`）をピンで固定する**（おすすめ） | manifest の SHA-256、再検証記録、スキーマピンの一致がすでに揃っている。ゲート判定 5（SHA 照合）をそのまま機械で検証できる。 | 支出 1 件ごとの計算のみであり、機能が小さい。 |
| B. M1 着手後に one-shot で新しく生成したものを使う | 最新の工場環境で生成した成果物を確認できる。 | 実行ごとに中身が変わり、判定基準が期限直前まで定まらない。所有者の手元環境に依存する。 |

### おすすめと理由
- **おすすめ**：A. 封緘済み bundle（`cm4-delivery-bundle-001`）をピンで固定する
- **理由**：受入ゲートは再現性のある確定した成果物で判定すべきであるため。one-shot 新規生成（連携 Lv1 の ③）は「工場から店頭まで通った」証拠として別途扱い、合否判定とは分離する。

## Q2. ゲートの判定 3 の「golden の期待値」を何とするか

### 何を決めるか
受入ゲート判定 3（「golden のシナリオどおりに入力し、結果が golden の期待値と一致する」）における、具体的なテスト入力と期待値の定義を決める。

### なぜ今決める必要があるか
事前宣言済みの受入条件には具体的な入力例や期待値が含まれておらず、現在のスキーマ v0.1 では複数支出をまたぐ全体精算（誰が誰へいくら渡すか）が表現できない（[`README.md`](./README.md) §2.3 参照）。着手前に期待値を再定義しておかないと、期限直前に判定基準が揺らぐため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. spec の computed の意味から期待値の表を作り、事前宣言し直す**（おすすめ） | 例（4 人で 4,000 円、A 立て替え → 1 人あたり 1,000 円、A 受取額 3,000 円）のような入力例と期待値を 3〜5 件固定し、着手前に確定できる。 | 支出ごとの計算に留まるため、企画書にある割り勘精算の姿とは差がある。 |
| B. 全体精算（誰が誰へいくら）までを M1 のゲートに入れる | 企画書の割り勘の姿に近くなる。 | スキーマ v0.2（全体参照・精算の標準関数）と golden の再封緘が必要となり、工場側の裁定待ちで M1 の 2 週間に収まらない。 |
| C. 判定 3（期待値の一致検証）自体をゲートから外す | 期待値の定義が不要になり、進めやすい。 | 合否判定が「画面が出た」だけになり、ゲートが形骸化する。 |

### おすすめと理由
- **おすすめ**：A. spec の computed の意味から期待値の表を作り、事前宣言し直す
- **理由**：判定基準を後から動かさないよう、着手前に期待値を固定すべきであるため。全体精算はスキーマ v0.2 の裁定（工場側）と合わせて M2 の Instant Runtime で扱う。なお、判定 3 の言い直しはゲート宣言の変更に該当するため、所有者が `../m0/05-acceptance.md` §7 に日付とともに追記する。

## Q3. スキーマ v0.1 が決めていない実行時の意味を、どう決めるか

### 何を決めるか
スキーマ v0.1 で構文のみが定められ、実行時の振る舞いが未定義となっている部分の解釈方針を決める（[`README.md`](./README.md) §2.4 参照）。

### なぜ今決める必要があるか
画面表示（Instant Renderer）や API（data-api）、データ保存（DO）の実装を進めるにあたり、未定義部分の解釈が定まっていないと実装に着手できないため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. MUSUNEST が最小限を決めて `appspec-schema` に文書で持つ**（おすすめ） | 工場側の裁定を待たずに M1 の実装を進められる。スキーマのバイト列は変更しない。 | 将来的に工場の verifier の前提とずれるリスクがある（ずれを発見した場合は工場側へ裁定を依頼する）。 |
| B. 工場側でスキーマを v0.2 に引き上げ、実行時の意味を決めてもらってから作る | プラットフォームと工場の解釈がそろった状態で作れる。 | 工場側の裁定待ちが発生し、golden の再封緘も必要となるため M1 の作業が止まる。 |

### おすすめと理由
- **おすすめ**：A. MUSUNEST が最小限を決めて `appspec-schema` に文書で持つ
- **理由**：M1 のスケジュールを阻害せず、自律して垂直スライスを通すため。スキーマ自体のバイト列は固定したまま、M1 の golden 動作に必要な範囲に絞って規約を文書化する。
- **M1 で決める範囲の案**：
  | 宣言項目 | M1 の解釈（案） |
  |---|---|
  | `number` / `string` | JSON の数値・文字列。`number` は有限の数のみ許可する。 |
  | `list` | 文字列の並び（空配列および重複要素は許容しない）。 |
  | `views`（type 指定なし） | その entity の一覧。各行に computed の計算値を並べて表示する。 |
  | `actions`（op 指定なし） | その entity への 1 件追加操作。validations を data-api で評価してから保存する。 |
  | `permissions` / `minIdentity` | `subject: minIdentity` かつ `mode: anonymous`。M1 は認証がないため、インスタンス URL を知っていれば誰でも読み書きできる（Q5 参照）。 |

## Q4. 「Form A の経路」を M1 でどこまで作るか（テンプレ #38 の扱い）

### 何を決めるか
企画書にある「Form A 経路（共通ホスト＋アドオン動的読み込み）」の構築範囲、およびテンプレート tarball の SHA 固定タスク（#38）の扱いを決める。

### なぜ今決める必要があるか
M1 のスコープを L2（spec のみ）に絞るか、L3/L4（アドオンコード実行・サンドボックス）まで広げるかによって、設計と実装工数が大幅に変わるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. L2（spec だけ）の経路に絞り、テンプレ（#38）は M2 へ移す**（おすすめ） | R2 の bundle（spec）→ data-api → host（Instant Renderer）→ DO の経路に集中でき、2 週間で確実に垂直スライスを通せる。 | 企画書の「実テンプレの確定・Form A 統合スモーク」のうち、テンプレ側の検証は M1 で完了しない。 |
| B. L3/L4 のアドオン動的読み込みまで作る | 将来の拡張経路（esbuild で束ねた `app-zone/` コードの動的実行）を先んじて検証できる。 | golden 割り勘にはアドオンコードが存在しないため検証できない。L4 の sandbox 設計等が必要となり、2 週間に収まらない。 |

### おすすめと理由
- **おすすめ**：A. L2（spec だけ）の経路に絞り、テンプレ（#38）は M2 へ移す
- **理由**：M1 のゲートおよび MVP 3 アプリで必要なのは L2 の配信経路のみであるため。テンプレ構成は、実物の Template App を開発する M2 で要件とともに決める方が手戻りを防げる。

## Q5. ログインが無い間、アプリの API をどこで有効にするか

### 何を決めるか
認証機能（Google OAuth）が未実装の M1 期間中、ミニアプリの API をどの環境で有効化するかを決める（[`README.md`](./README.md) §7.3 参照）。

### なぜ今決める必要があるか
現状の CD パイプラインでは、main マージで staging へ、v タグ付与で production へ自動デプロイされるため、未認証の書き込み可能エンドポイントが本番環境へ露出するリスクを制御する必要があるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. dev・staging だけで有効化し、production では 404 を返す**（おすすめ） | production に不要なデータが書き込まれるリスクを確実に遮断できる。CI/CD パイプラインを止めずに済む。 | 環境別の分岐処理が 1 つ増える（`vars.ENVIRONMENT` で判定し、テストで固定する）。 |
| B. M1 の間は production への v タグを一切打たない | コードに環境分岐を追加せずに済む。 | セキュリティ修正など、他の重要な修正を production に出せなくなる。 |
| C. production でも API を有効化する | 全環境で同一の動作コードを維持できる。 | URL を知る第三者なら誰でも production の DO に書き込める状態となる。 |

### おすすめと理由
- **おすすめ**：A. dev・staging だけで有効化し、production では 404 を返す
- **理由**：production へのデプロイ経路を塞ぐことなく、未認証 API の公開リスクを確実に防ぐため。

## Q6. bundle をどう配るか（R2 に置いて登録する経路）

### 何を決めるか
CommandAgent が生成した bundle を、Cloudflare（R2 および D1）へ配置・登録するための配布手段を決める。

### なぜ今決める必要があるか
M1-1（ミニアプリ配信）を成立させるために、配布スクリプトの配置場所や実行権限の設計を確定させる必要があるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. 手元のスクリプト（publish）で manifest とピンを照合し、R2 配置と D1 登録を行う**（おすすめ） | 新たな管理用 API や認証機構を作らず、最小限の実装で安全に配布できる。 | 開発者がローカル環境から手動で実行する必要がある（`.env` の staging 資格情報を使用）。 |
| B. data-api に管理用 API を新設してそこへ送る | 将来の自動化に向けた API 基盤を先んじて整備できる。 | data-api は外部ルートを持たない規律であるため、gateway への管理用入口と認証が必要になり、M2 の認可より先に作ることになる。 |
| C. Builder Plane から Queue 経由で自動配信する | 手動作業が発生しない。 | M2 で予定している連携 Lv2 の範囲であり、M1 のスコープを超える。 |

### おすすめと理由
- **おすすめ**：A. 手元のスクリプト（publish）で manifest とピンを照合し、R2 配置と D1 登録を行う
- **理由**：M1 では最小限の構成で確実に垂直スライスを通すため。なお、手元スクリプトから R2 / D1 へ直接書き込むのは、CD が D1 マイグレーションを実行するのと同様の「運用者操作」であり、「Data API が唯一の権限強制点」というリクエスト経路の規律には抵触しない。

## Q7. L2 の bundle の assurance: partial を受け入れるか

### 何を決めるか
CommandAgent の生成結果に含まれる検証保証ラベル `assurance: partial` を、MUSUNEST の受入基準として許容するかどうかを決める。

### なぜ今決める必要があるか
CommandAgent の headless 規律では「呼び出し側は verdict と assurance の両方で合否を判定する」と定められているため、プラットフォーム側での受入検査ルールを明文化しておく必要があるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. L2 は `verdict: full` を必須とし、`assurance` は `partial` 以上を受け入れる**（おすすめ） | golden bundle をそのまま受入可能となる。実行時スモークの不足分は MUSUNEST の e2e で担保する。 | 受入ルールを成果物の水準（L2 と L3/L4）で分けて管理する必要がある。 |
| B. `assurance: full` を常に必須とする | 全成果物に対して工場側での完全な画面検証を要求できる。 | golden bundle が受入不合格となる。L2 は画面コードを含まないため工場側で画面スモークを実行できず、原理的に L2 成果物が通らなくなる。 |

### おすすめと理由
- **おすすめ**：A. L2 は `verdict: full` を必須とし、`assurance` は `partial` 以上を受け入れる
- **理由**：L2 における `verdict: full` は「spec の検証は完了した。実行時のスモークはプラットフォーム統合側が受け持つ」という契約上の定義に合致しているため。画面での動作検証は MUSUNEST 側の e2e で被覆する。

## Q8. 決定的な再検証をどこで実行するか

### 何を決めるか
CommandAgent の成果物に対する決定的再検証（offline verifier による同一性確認）をどの環境で実行するかを決める。

### なぜ今決める必要があるか
M1-2（CommandAgent 連携 Lv1）の完了条件 ④ を満たす実行基盤と、CI パイプラインへの影響を確定させる必要があるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. 所有者の手元環境で実行する**（おすすめ） | CI に Rust ツールチェーンや外部バイナリを持ち込まずに済む。ピン固定された CommandAgent バイナリの SHA-256 を照合した上で実行する。 | CI ログとして自動記録されないため、手順を runbook にまとめて実行記録を残す運用が必要となる。 |
| B. GitHub Actions（CI）上で実行する | プルリクエストごとに再検証が自動実行され、客観的な証跡が残る。 | ビルド時にネットワーク越しで外部バイナリを取得できない制約（ピンの規律）と衝突し、CI に重いツールチェーンが必要となる。 |

### おすすめと理由
- **おすすめ**：A. 所有者の手元環境で実行する
- **理由**：CI の軽量性とリポジトリのピン規律を維持するため。なお、manifest の照合（全ファイルの SHA-256・構成確認）は TypeScript で実装可能であるため、こちらは CI（e2e）で毎回自動実行する。

## Q9. ピン差し替えの儀式（1回）の対象は何か

### 何を決めるか
M1-2 の完了条件 ② にある「ピン差し替えの儀式（照合 → 回帰 → 更新 → 記録）」の対象とする成果物を決める。

### なぜ今決める必要があるか
現在 `pins/commandagent.json` で管理されている要素のうち、M1 の開発スコープ内で実際に更新可能な対象を特定しておく必要があるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. golden bundle のピンを追加する**（おすすめ） | `pins/commandagent.json` に bundle manifest の SHA-256 を新規登録し、あわせて CommandAgent の revision 整合性を確認する。 | 既存ピンの「差し替え（置換）」ではなく「新規追加」の形となる（旧→新の置換は工場の revision 更新時に実施）。 |
| B. テンプレートの tarball（#38）を差し替える | 既存の未解決ピン（null）を正式な値で埋めることができる。 | Q4 でテンプレート関連を M2 へ移す決定をした場合、M1 では実施できなくなる。 |
| C. CommandAgent の revision を新しい版へ差し替える | 工場本体のバージョンアップ手順を実演できる。 | 2026-09-15 時点で main ブランチの revision（`031ec74`）が進んでおらず、差し替え先の新しい版が存在しない。 |

### おすすめと理由
- **おすすめ**：A. golden bundle のピンを追加する
- **理由**：M1 で確実に実在する成果物を対象にし、ピン管理手順の検証（runbook 化）を達成できるため。

## Q10. M1 の着手日（ゲートの期限の起点）

### 何を決めるか
受入ゲートの完了期限（着手から 2 週間）の起点となる「M1 着手日」をいつにするかを決める。

### なぜ今決める必要があるか
受入条件（`../m0/05-acceptance.md` §7）に明記されている期限のカウントダウンを開始し、マイルストーンの進行基準を確定させるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. Q1〜Q9 の判断が完了し、M1 の Issue を起票した日を着手日とする**（おすすめ） | 未決定事項による手戻りリスクを排除した上で、実装作業の実質的な開始と期限を一致させられる。 | すべての判断が完了するまで着手日の日付が未定となる。 |
| B. 未決定の問いが残っている段階であらかじめ特定の日付を固定する | スケジュールの終了目標日が早期に確定する。 | 意思決定の遅延がそのまま 2 週間の開発期間を圧迫するリスクがある。 |

### おすすめと理由
- **おすすめ**：A. Q1〜Q9 の判断が完了し、M1 の Issue を起票した日を着手日とする
- **理由**：判断が不完全な状態でタイマーを開始させないため。決定した日付は所有者が `../m0/05-acceptance.md` §7 の空欄（`____-__-__`）に追記する。

## Q11. リアルタイム同期（DO の WebSocket）を M1 に入れるか

### 何を決めるか
Durable Object の WebSocket 接続を用いたリアルタイムデータ同期機能を、M1 の実装範囲に含めるかどうかを決める。

### なぜ今決める必要があるか
画面（host）とサーバー（DO）の通信の作り方と、Cloudflare 無償枠への効き方の調査・実測に関わるため。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. M1 には含めず、M2 で実装する**（おすすめ） | 設計と実装を大幅に簡素化でき、2 週間の期限内に確実に垂直スライスを通せる。 | 複数端末で同時に開いた場合、相手の変更を見るには手動での画面再読み込みが必要となる。 |
| B. M1 のスコープにリアルタイム同期を含める | 最初から即時反映されるモダンな協調 UI を実現できる。 | WebSocket の接続維持や休止状態のハンドリングが必要となり、無償枠への影響調査と実装工数が 2 週間に収まらない。 |

### おすすめと理由
- **おすすめ**：A. M1 には含めず、M2 で実装する
- **理由**：M1 のゲート判定 4 は「再読み込みまたは別端末で開いたときにデータが保持されていること（永続化）」であり、即時同期までは求めていないため。まずは HTTP リクエストによる確実な読み書きを成立させる。

## Q12. spec を Worker でどう持つか（CPU 10 ms 対策）

### 何を決めるか
ミニアプリの仕様定義（`app.spec.yaml`）を Cloudflare Workers 上でどのように保持・解釈し、CPU 時間 10 ms 制限を遵守するかを決める。

### なぜ今決める必要があるか
リクエストごとの YAML 解析や静的検査は CPU を使い、無償枠の上限（10 ms）や昇格トリガー（P-1）に関わるため、データの配置と前処理の方針を先に決める必要がある。

### 選択肢
| 選択肢 | 良い点（メリット） | 気になる点（デメリット・課題） |
|---|---|---|
| **A. R2 に原本（YAML）を置き、publish 時に検査済み・正規化済みの形（JSON）も生成して併せて配置する**（おすすめ） | Worker 実行時のパース処理と静的検査を省略でき、CPU 時間を抑えられる。原本と解析結果を R2 で一元管理できる。 | 原本と正規化形式の同一性を SHA 等で関連付けて管理する仕組み（JSON 側に原本 SHA を保持など）が必要となる。 |
| B. API リクエストのたびに R2 から YAML を取得してパースと静的検査を行う | R2 に YAML 原本のみを置けばよく、publish スクリプトの事前処理がシンプルになる。 | YAML のライブラリの大きさと解析の CPU が 10 ms の上限に効く。 |
| C. インスタンス生成時に各 DO の内部ストレージ（SQLite）へ正規化済み spec を持たせる | 一度インスタンスを作れば R2 へのアクセスなしに DO 内で高速に spec を参照できる。 | アプリの spec 更新時に、同一 bundle を参照する多数の DO に対して個別に更新を伝播させる必要が生じる。 |

### おすすめと理由
- **おすすめ**：A. R2 に原本（YAML）を置き、publish 時に検査済み・正規化済みの形（JSON）も生成して併せて配置する
- **理由**：10 ms に収めやすくしつつ、DO のストレージ管理をシンプルに保つため。なお、どの方式を採る場合でも、staging 環境で spec 読み込みと computed 評価の CPU 時間を実測し、`../m0/06-plan-and-limits.md` の昇格トリガーに照合する。
